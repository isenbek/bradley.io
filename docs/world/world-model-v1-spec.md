# World Model v1 — Design Spec & Data Asks

A proposal for v1 of the “how Spice works” world model, intended to be consumed by an
orchestrator agent coordinating ~10–15 domain-specialized Claude Code agents. Builds on
the bradley.io session-stats infrastructure described in `SESSION-STATS.md`.

-----

## 1. What I think we’re building

A single JSON artifact — call it `world-model.json` — that the orchestrator (and
optionally individual agents) loads at session start. It encodes:

1. **Cross-cutting facts** — things true regardless of domain (e.g. “the UI toolkit is
   Loom”, “we deploy under a modular factory pattern”, “treat software as commodity,
   moat is detail + speed”). These are the things you currently re-explain.
1. **Per-domain profiles** — patterns specific to each agent’s tier (infra, UI, backend
   service, deployment, etc.). Communication norms, preferred tools, common
   corrections, the shape of how work gets done in that domain.
1. **Repetition map** — the instructions/preferences you’ve had to inject more than
   once. This is the highest-value part: every entry here is a sentence the orchestrator
   can pre-load so you stop having to say it.

The world model is read-only at agent runtime. It’s regenerated by a new pipeline step
(`world-model-pipeline.py`) on the same 4h cadence as everything else.

-----

## 2. What’s already done vs. what’s missing

### Already built (we lean on these)

- Project-directory siloing → primary domain signal, free.
- `ai-pilot-pipeline.py` keyword classification → weak domain labels per session.
- `stats-cache.json` → daily activity ground truth.
- `~/.claude/plans/` → structured plan corpus (problem-solving signal).
- `~/.claude/history.jsonl` → every prompt you’ve typed (communication-style signal).
- DC-0 + DC-1 mirror → unified corpus.

### What’s missing

- Mapping from project-dir → agent tier. Some dirs are obvious (`bradleyio`, `cbai`),
  others may not be. Need a curated table.
- Repetition mining. Nobody is currently extracting “things Spice keeps saying.”
- Correction detection. Nobody is currently detecting “Spice immediately followed
  the assistant message with a correction.”
- A consumer-friendly output schema designed for orchestrator ingestion.

-----

## 3. V1 design

### Pipeline stages

**Stage A — Session classification**
For each `*.jsonl` under `~/.claude/projects/` and `~/.claude-dc1/projects/`:

- Decode project dir → repo path.
- Look up agent tier from a curated `project-to-tier.yaml` (UI / backend / infra /
  data / research / etc.).
- Pull existing keyword-domain label from `ai-pilot-data.json` if present.
- Output: `{session_id, project, tier, ai_pilot_domain, started_at, ended_at, message_count, tool_calls}`.

**Stage B — Pattern extraction (per session)**
Walk the JSONL events and emit features:

- **Communication features**: avg user-message length, avg assistant-message length,
  ratio, presence of correction tokens (“no”, “actually”, “instead”, “wait”, “stop”),
  presence of approval tokens (“perfect”, “yes”, “ship it”, “good”).
- **Problem-solving features**: tool-use sequences (counts and order), plan-mode
  invocations (cross-ref `~/.claude/plans/`), edit-vs-create ratio, test-run frequency.
- **Correction events**: any user message that immediately follows an assistant
  message and contains a correction token. Capture the user message text + a snippet
  of what the assistant just did. These are the gold mine.

**Stage C — Repetition mining**
Across all sessions, find user messages or fragments that:

- Recur ≥3 times across distinct sessions, AND
- Are not generic (“ok”, “thanks”, “continue”) — filter via stoplist + min length.
  Cluster near-duplicates with simple normalized-edit-distance. Emit a ranked list of
  the most-repeated instructions per tier and globally.

These are the candidates for “things to bake into the world model.” Manual review pass
optional but recommended for v1 — let’s not auto-promote raw user text into a system
prompt without a sanity check.

**Stage D — Profile assembly**
Aggregate stages B and C by tier:

- Per-tier profile: typical communication pattern, preferred tools, top corrections,
  top repeated instructions.
- Global profile: repeated instructions that appear across ≥N tiers (these are the
  cross-cutting facts).
- Manually-curated `philosophy.md` slot: stuff like “software-as-commodity, moat is
  detail and speed, hide the messy bits behind a normalized platform.” V1 just embeds
  this verbatim from a hand-edited file you control. We don’t try to derive it.

### Output schema (sketch)

```json
{
  "version": 1,
  "generatedAt": "2026-05-02T12:00:00Z",
  "philosophy": {
    "source": "philosophy.md",
    "text": "..."
  },
  "globalFacts": [
    {"id": "ui-toolkit", "fact": "The UI toolkit is Loom.", "confidence": "manual", "evidenceSessionCount": 47},
    {"id": "ui-arch",    "fact": "Frontend is Loom; backend is modular services.", "confidence": "manual"}
  ],
  "tiers": {
    "ui": {
      "agentName": "ui-agent",
      "projectDirs": ["-home-bisenbek-projects-loom", "..."],
      "communicationProfile": {
        "userMessageMedianTokens": 28,
        "correctionRate": 0.12,
        "preferredCadence": "iterative"
      },
      "preferredTools": ["edit_file", "view", "bash_tool"],
      "repeatedInstructions": [
        {"text": "Use Loom primitives, not raw HTML.", "occurrences": 14},
        {"text": "Mobile-first; iOS Safari is the canary.", "occurrences": 9}
      ],
      "commonCorrections": [
        {"pattern": "wrong-component-import", "examples": ["..."]}
      ]
    },
    "infra": { "...": "..." },
    "backend": { "...": "..." }
  },
  "unsorted": {
    "repeatedInstructions": [
      {"text": "...", "occurrences": 3, "tiers": ["ui", "backend"]}
    ]
  }
}
```

The `unsorted` bucket is intentional — for v1, anything we can’t confidently assign to
a tier goes there for manual triage. Better than dropping signal.

## 5. Open design questions

These are calls I’d rather make with your input than guess at.

1. **Where does the world model live and how do agents consume it?**
   Options: (a) drop in each project’s `CLAUDE.md` at orchestrator-init time, (b)
   serve via local HTTP and have agents fetch on demand, (c) the orchestrator passes
   relevant slices into each subagent’s system prompt. I’d lean (c) — keeps the per-agent
   context lean and lets the orchestrator decide what’s relevant. Your call.
1. **How aggressive on repetition mining?**
   Strict (≥3 occurrences, manual review before promotion) is safe but slow. Loose
   (≥2 occurrences, auto-promote) is fast but risks turning one-off frustrations into
   permanent system instructions. I’d recommend strict for v1.
1. **Do we model the *evolution* of your style, or treat the corpus as flat?**
   You mentioned your approach has evolved. V1 flat is simpler. V2 could weight recent
   sessions higher or detect drift. Flagging this so we don’t bake in flat-forever.
1. **Confidence/provenance.** Every fact in `world-model.json` should carry a source
   (manual, mined, weak-label). The orchestrator can then decide how much to trust
   each. Suggest we enforce this from v1.
1. **Privacy / scope.** The Claude.ai export under `docs/spicy-claude-web/` includes
   personal chats. V1 should probably stay within `~/.claude/projects/` (work) and
   skip the consumer export, unless you want it explicitly in scope.

## 6. Phase 2 ideas (parking lot)

Not for v1, but worth noting so we don’t paint into a corner:

- Embedding-based clustering of corrections and instructions (smarter than
  edit-distance dedup).
- A “suggest new world-model fact” loop — when a user message correlates with a
  correction across sessions, propose adding it.
- Per-session “style fingerprint” so the orchestrator can spot when a session’s
  going off-pattern (e.g. you’re frustrated, or you’ve changed your mind).
- Closed-loop: orchestrator logs which world-model facts it injected per session;
  pipeline measures whether injection reduced correction rate. Real ground-truth eval.
